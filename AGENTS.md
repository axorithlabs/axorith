# AGENTS.md

- Do not use Git commands to undo or discard changes. In particular, do not use `git checkout`, `git restore`, `git reset`, `git revert`, or any other Git command for rollback or deletion. Edit files directly and preserve unrelated changes.
- If a bug-fix attempt does not fix the bug, first remove only the code introduced by that failed attempt. Then try a different fix; do not layer it on top of the failed attempt. Preserve unrelated changes.
- Keep permanent behavioral and regression tests, including tests added to reproduce and fix production incidents. Delete only disposable investigation probes and their exclusive fixtures; never delete a useful regression because the bug is fixed.
- Every feature or bug fix must update permanent tests through its production API or ViewModel command. Cover failures, rollback, persistence/restart and observable side effects where applicable; select the corresponding native or installer gate when the behavior depends on that environment.
- Exercise the production component and assert an observable result: persisted data read by a fresh instance, actual process lifetime, blocking/unblocking, received protocol payload, or Host/Client state. Benchmarks must measure real operations.
- Test doubles may represent external boundaries or inject failures into an orchestration test. Never replace the component under test, pre-program the result being asserted, or claim a simulated boundary proves real browser, Windows, or installer behavior.
- Product catalog regressions must use shipped module manifests and real persistence/API paths. A fabricated catalog of retired modules only verifies explicit legacy compatibility.
- A regression must recreate its distinguishing conditions (for example, two different Workspaces for a foreign stop schedule). Assert exact values and negative effects; a success flag, message type, file existence, or mock invocation alone is insufficient when the feature promises more.
- Round-trip tests must deserialize into a different instance with a different value. Fallback tests must start with a non-default value. Async tests must wait for an observable condition with a bounded deadline, clean up their subscriptions/processes, and fail on unexpected errors.
- Timeout tests must let the production deadline cancel a pending operation and verify rollback; injecting an OperationCanceledException alone does not exercise the timer. Concurrent-file regressions must overlap real readers and writers, then verify complete data through a fresh instance.
- Preserve useful existing tests. Remove confirmed tautologies, redundant cases, unused fixtures, and tests of dependency internals only after checking that product behavior remains covered. During an audit inspect every test and its production path.
- Run tests in isolated data directories and stop only processes owned by the test. Never install/uninstall, alter sign-in protection, reboot, shut down, or modify the user's browser profile on the development machine. Use a disposable Windows Sandbox/VM for destructive system and installer E2E.
- Do not create audit or report files (for example, `REPORT.md`, `AUDIT.md`, or similar) unless the user explicitly requests them.
- Keep build outputs and logs in the existing directories. Do not change output, log, or build directory settings or add task-specific build configurations/directories; use the existing `build/Debug` and `build/Release`, not paths such as `build/AuditBugs`.
- Write commit subjects in Conventional Commit format: `<type>(<scope>): <imperative summary>`. Omit the scope when it adds no useful context. Use `feat` for new functionality, `fix` for bug fixes, and `chore` for maintenance or documentation; use other standard types as appropriate.
- Do not create commits unless the user explicitly asks you to commit in the current conversation.
- Before running `dotnet build` or `dotnet test`, disable Avalonia build telemetry for that command/session by setting `AVALONIA_TELEMETRY_OPTOUT=1` (in PowerShell: `$env:AVALONIA_TELEMETRY_OPTOUT = '1'`). Do not change the user's persistent environment.
- Restore with the same Configuration as the build (`dotnet restore Axorith.sln -p:Configuration=Release` before a Release `--no-restore` build); this repository keeps intermediate NuGet assets separately in `build/Debug` and `build/Release`.
- Keep warnings-as-errors and the redundancy/performance rules enabled. Fix diagnostics rather than disabling analyzers, adding broad suppressions, or bypassing `Directory.Build.rsp` to obtain a passing build.
